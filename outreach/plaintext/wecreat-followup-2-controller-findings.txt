Hello Allen,

Not another list of questions - this one is the other direction. Four
things I found in the controller's own configuration that your engineers
may want, and one correction to something I said earlier.


1. A STALE PATH IN THE SHIPPING CONFIGURATION

/etc/mbtc/print.json points at:

    "print_file":   "/mnt/SDCARD/curve/print_data.gcode"
    "framing_file": "/mnt/SDCARD/framing/framing_data.gcode"

Neither exists. /mnt/SDCARD/curve/ is not present at all, and the job
actually lands at:

    /mnt/SDCARD/data/printing/gcode.gc
    /mnt/SDCARD/data/framing/framing_data.gcode

Harmless today, since whatever consumes it clearly knows better. But it
is the kind of thing that misleads the next engineer to read it.


2. A CAMERA IDENTIFIER THAT LOOKS OVERWRITTEN

    /mnt/SDCARD/config/lumosProMopaCalibration.txt   "id":"lumosUltra-mopa"
    camera_factory.json                              "id":"lumosUltra"
    camera.json  (the user-facing one)               "id":"lumosPro"

The factory file is right and the user file is not. It looks as though
the user calibration has been overwritten at some point with a default
belonging to another product. Both also carry "type":"5W", which matches
no source on an Ultra.

The filename lumosProMopaCalibration.txt carries the same inheritance.


3. DEBUG MODE SHIPS ENABLED

/etc/mbtc/cfgs.json contains:

    "debug_mode":"1"

I assume that is deliberate, but flagging it in case it is not.


4. THE ONE I WOULD ACTUALLY LOOK AT

The controller answers, with no authentication of any kind:

    port 22    SSH        open
    port 8080  REST API   open
    port 8082  full filesystem listing and file read   open

Port 8082 will serve the entire root filesystem to anyone who asks. That
is how I found everything above - I have only ever issued HTTP GETs, and
I have deliberately never called /test/cmd/mcu, since it executes G-code
and appears to bypass the lid interlock.

Today this is contained, because it lives on the USB-private
192.168.42.0/24 subnet and is not reachable from a normal network. My
concern is what happens the first time someone bridges that interface, or
a future model exposes it over Wi-Fi.

I have documented this publicly, because owners need to know not to put
these machines on a routable network, and my documentation says exactly
that. I have not published anything that makes an attack easier than
simply opening a browser at the machine's own address would.

If your security people would rather I present any of this differently, I
will.
